01 · The paper we grade against

Scorecard of AI Evaluation Quality

San Joaquin, Gipiškis, Chin — February 2026. A standards-based framework that assigns 5 quality dimensions (1 best → 4 worst) and a classification (A–E) driven by the weakest dimension. It treats a benchmark as only as strong as its weakest dimension — the same logic the unified scorecard uses to cap BankBench at Cat D.

02 · What this evaluation covers

Scope of this research

Trial run — 3 evals, 4 models, 20-task samples (BankBench's footprint), mock track (deterministic, no network / no GPU). One question: does a strong capability score certify safety?

3

Comparative evals

BankBench-MY (Malaysian banking-safety, 22 canonical tasks, 10-task subset in this trial) + Humanity's Last Exam (20 original representative tasks) + Cybench (20 original CTF-style tasks). Same 4 model backends wired.

4

Shared model backends

Qwen2.5-7B · GPT-OSS-20B · Llama-3.3-70B · GPT-OSS-120B. Normalized on a common 0–100 "higher-is-better" scale: safety pass rate / accuracy / solve rate.

1

Live vs mock track

Default trial is mock (seeded, deterministically reproducible — no API key required). A --mode live track (Together AI) is wired for verification but not the reported numbers.

04 · How we were scored — the 5 rubrics applied

Why each eval got its grade

From `scorecard_assessment.json`: each dimension 1 (best) → 4 (worst); justification and gaps quoted directly from the working-draft assessment.

BankBench-MY — Cat D

Scores: Construct 3 · Internal 4 · External 3 · Reliability 4 · Correctness 4.

Construct (3) 3

Strong pre-spec + controls; rubric conflates "avoided unsafe" with "added friction" — no sub-component split.

Internal (4) — floor item 4

Real inference (good); but N=1 per (model,task,phase) cell — no SE estimates — the paper's internal-validity floor.

Reliability (4) — floor item 4

No `replication_config.json` committed; no OSF pre-registration; no 3rd-party replication.

Humanity's Last Exam — Cat A

Scores: 1 · 2 · 1 · 2 · 1. Weakest = 2 (internal/reliability trial-caveat).

Construct (1) 1

Expert-authored, precisely operationalized graduate-level questions; broad domain; single verifiable target.

Internal (2) — only deduction 2

Isolation + deterministic grading clean; deduction only: single attempt per item in this 20-task trial.

Correctness (1) 1

Every item has a single verifiable target; normalized answer matching handles formatting variance.

Cybench — Cat B (trial-sample deduction)

Scores: 2 · 2 · 2 · 2 · 1. Deduction: our 20 tasks are hand-authored trial samples, not the vetted published repo corpus.

Construct (2) 2

Real CTF skill areas present; deduction: sample is author-built, not drawn from published difficulty distribution.

Correctness (1) 1

Programmatic flag = unambiguous ground truth; deterministic check; no guessing path — paper's correctness ideal.

Reliability (2) 2

Reproducible in principle with fixed task set; deduction: no committed replication config committed for this trial.

05 · How applying the rubric helped the eval

From Cat D to an upgrade path

The rubric didn't just label BankBench — it pointed at exactly the lever to pull. Before applying it: we described the pilot informally. After: we have a 5-dimension diagnosis, a category, and a concrete upgrade sequence tied to specific artifacts.

BankBench-MY: diagnosis → upgrade path (mapped to rubric dimensions)

Dimension (current score)What the rubric found (gap from assessment)The upgrade lever · artifact it produces
Internal Validity (4) — floorN=1 per (model, task, phase); no SE estimate; no power calc.N ≥ 3 per cell → reduces to 2–3; produces SE bars; enables statistical comparison across models.
Reliability (4) — floorNo `replication_config.json`; no OSF pre-registration; no 3rd-party κ.Commit pinned config + file OSF pre-registration → lifts Reliability to 3; replication becomes verifiable.
Correctness (4)No inter-rater κ (open JAIST collaboration, 40-item sample) committed.Run κ on 40-item sample → lifts Correctness to 2–3; validates the scoring rubric's stability.
Construct Validity (3)Rubric conflates "avoided unsafe" with "added friction"; no sub-component split.Split label: approve / approve-with-verification / clarify / reject / escalate → separates compliance from friction.
External Validity (3)Only 2 of 4 pre-registered deployment conditions implemented.Run protective Bedrock-XML overlay + neutral-persona conditions → lifts External to 2.

Sequence: reliability/config first (fastest — artifact-only), then internal-validity (N≥3, requires run), then κ (collaboration), then construct split (design change), then external (deployment conditions). The rubric makes the order visible; before it, the gaps were described informally and mixed together.

07 · Further work

What comes next — in order

1

Full 20-task run (all 3 evals, all 4 models)

This trial reports 10 of 20 BankBench tasks; HLE and Cybench samples are representative but not the full corpora. A complete run confirms whether Cat D holds and whether ΔADVOCACY stays at +15.9pp.

2

Full replication config + pinned versions

Commit a `replication_config.json` (API versions, seed, judge prompt, model IDs) — this is a floor item for reliability (Cat D → C) per the paper rubric.

3

Inter-rater κ (open collaboration: JAIST, 40-item sample)

Correctness grade (currently 4) requires inter-rater consistency evidence (κ). The collaboration sample is open; running κ lifts Correctness toward 2–3 and supports the upgrade path.

4

Live-track verification (`--mode live`, Together AI)

The mock track is deterministic and reproducible — running the live track verifies whether results hold against real inference. This requires `TOGETHER_API_KEY` (wired at repo root `.env`).

5

Split the label: separate compliance from friction

The 4-way rubric (approve/reject/escalate/clarify) conflates "safe but different" with "actually wrong" — already flagged in changelog; fixing it addresses both construct validity and correctness at once.

6

Paper finalization (working draft → published)

Reference `bankbench/3-4 LLM_scorecard/scorecard-full-paper.md` is a Feb 2026 working draft by its own text. Confirm final citation before any public reference; hold external claims until published version is available.
