skeleton · the shell before the content

The page shell, with every slot named before anything is built into it.

This file is the structural reference for the Operational Integrity Evals microsite. It carries the shared nav, footer, type scale, colour tokens, and section rhythm — the same shell that index.html renders as a finished home page.

Each block below is a slot: an id, a purpose, the content that belongs in it, and the build phase it lands in. Slots drawn as dashed wireframes are ghost elements — deliberately unbuilt, and labelled as such so nothing here reads as a shipped feature.

Shell reused by

index.html — home page with the interactive harness demo. Both files link the same ops.css, so tokens never drift between them.

Content source

ais-research-companion/outreach/government/ops-eval.md — the full method write-up this site presents.

Convention

Ghost elements always carry a text label. Wireframe styling is a visual cue, never the only signal that something is unbuilt.

the slots

Reading order, top to bottom

The order below is the order a first-time reader meets the method: the problem, then the tool, then the evidence, then what they can buy. Slot ids match the anchor targets in index.html.

00 · nav.top built · shared shell

Sticky bar: logo lockup, methodology badge, five section links, one conversion CTA. Identical markup in both files.

Owns: logo-box · wordmark · methodology-badge · nav-links · nav-cta

01 · #hero built · index.html

The sharp question the method answers, stated once. Two-column: framing on the left, three fact boxes on the right, then a marquee strip of the operational realities that motivate the work.

Owns: hero-grid · fact-box · hero-meta marquee

02 · #demo built · index.html

The proof. Four controls (scenario, behavioural risk profile, pressure condition, harness on/off) driving a decision-pathway trace and a ten-measure scorecard delta, recomputed on every change.

Owns: demo-controls · chips · trace · scores · demo-delta · demo-foot · Data: pre-authored synthetic outputs, labelled illustrative

03 · #map built · index.html

The causal-impact map: eight layers, each expanding to the "why did that happen" chain that runs effect back to operational cause. Native details accordion, no JS.

Owns: chain · chain-row · chain-layer · chain-body

04 · #profiles built · index.html

The profile library: five risk domains with non-stigmatising, testable labels, plus the integrity note on non-cash inducements.

Owns: tbl · tbl-note

05 · #scenarios built · index.html

The six IDFR-oriented scenarios as cards, each naming its primary risk domain, the pressure it applies, and the guards on what may be modelled.

Owns: grid-2 · card · card-index · card-tag

06 · #harness built · index.html

The ten harness components as a function table, plus the minimum experiment design — the matrix, the run count, and why one cherry-picked output proves nothing.

Owns: tbl · grid-3 · card

07 · #measures built · index.html

The measurement scorecard: ten separated failure modes with the question each answers and an example signal. Deliberately not collapsed into one ethical score.

Owns: tbl

08 · #screens ghost · not built

Where the unbuilt screens are declared. Four Phase 1 targets as ghost cards, plus ghost strips for Phase 2 and Phase 3. This is the honest boundary between the demo and the product.

Owns: ghost-card · ghost-tag · wire · ghost-bars · ghost-note

09 · #outputs built · index.html

The policy package every pilot produces: one-page executive brief, draft agent deployment policy, and procurement clauses.

Owns: grid-3 · card · rule · list

10 · #offers built · index.html

The seven offer/buyer/deliverable/revenue rows, and the realistic first commercial package — a Diplomatic AI Agent Assurance Pilot.

Owns: tbl · consult-panel

11 · #safeguards built · index.html

The method's own governance commitments — synthetic risk conditions, matched cases, no evasion recipes, multi-scorer rubrics, descriptive-not-causal claims.

Owns: grid-2 · card · list.check

Closing pair of CTAs and the footer note. Identical in both files.

Owns: contact-row · btn-primary · btn-secondary · footer-inner · footer-note

build order

Start with a clickable, data-light prototype

The phase sequence comes straight out of the method write-up. Phase 1 is what a stakeholder should be able to click through before any orchestration work is funded.

PHASE 1 · now

A credible demonstration

Scenario builder, decision pathway view, comparison dashboard, policy translator — using fictional cases and pre-authored model outputs.

  • built Shell, home framing, and the harness demo
  • ghost Interactive scenario builder
  • ghost Full decision pathway view
  • ghost Exportable comparison dashboard
  • ghost Policy translator
PHASE 2 · after design sign-off

Structured experiment capability

Repeatable runs only once the framework itself has been accepted by the people who would use it.

  • Scenario templates and parameter variation
  • Controlled profile conditions
  • Independent evaluator scoring
  • Versioned evidence packs
  • Harness configuration comparison
  • Exportable audit and policy reports
PHASE 3 · institutional productisation

Domain packs and public infrastructure

Where the method leaves the prototype and becomes something an institution runs itself.

  • Domain packs: diplomacy, service delivery, banking, procurement, local government
  • A Malaysian public-sector control catalogue
  • Trainer certification and train-the-trainer workshops
  • A cross-agency benchmark and anonymised learning network

ghost elements

What is drawn here is drawn on purpose

Ghost elements mark the boundary between what exists and what is proposed. They use three cues together — dashed outline, hatched fill, and a written ghost label — so the signal survives greyscale printing and screen readers alike.

built — shipped in this MVP ghost — proposed, not built

Content that exists in the MVP. Standard border, standard fill, no hatching.

ghost · example

Ghost card

Dashed border, hatched fill, explicit label. Reserved for the four Phase 1 screens and the Phase 2 and 3 roadmap items.

ghost · example

Ghost chart

Wireframe bars stand in for a chart that has no data behind it yet.

Rule of thumb: if a ghost element would read as a working feature to someone skimming the page, it is labelled too quietly. Add the words before adding more styling.
